What is Docker04 / 20

A platform for building, shipping, and running apps in containers.

Docker is a platform for building, shipping, and running applications inside containers. A container packages your application together with everything it needs to run — code, runtime, libraries, and system tools — so it behaves the same on any machine.

BUILD
Package code, runtime & libraries into an image
→
SHIP
Push the immutable image to a registry
→
RUN
Start identical containers anywhere
💡

"It works on my machine" → With Docker, your machine ships with the app. The environment travels with the code, so it runs the same on a laptop, in CI, and in production.

Containers vs VMs05 / 20

Virtualize the OS, not the hardware.

A VM virtualizes hardware and runs a full guest OS. A container virtualizes the OS and shares the host kernel — far lighter.

PropertyVirtual MachineContainer
IsolationFull OS per VMShares host kernel
SizeGigabytesMegabytes
StartupMinutesSeconds
OverheadHigh (hypervisor)Low
Layered stack — containers share the host kernel, so they drop the guest OS and hypervisor entirely.
Key Insight06 / 20

A container is just your app's processes in an isolated bubble.

A VM boots an entire operating system — its own kernel, drivers, init system, services — on top of virtualized hardware. That's why a VM is measured in gigabytes and takes minutes to boot. A container is just your app's processes running in an isolated bubble on the host's already-running kernel. No second OS to boot — so it starts in seconds and weighs megabytes.

🛡️

Namespaces — isolation

A Linux kernel feature that gives each container its own view of the system: PID tree, mount table, network stack, hostname, user IDs. The container thinks it is alone on the machine, even though it shares the kernel.

🎚️

Cgroups — resource limits

Control groups cap how much CPU, memory, block I/O, and network a container can consume. One container cannot starve its neighbours, even on a shared host.

◆

Docker did not invent these — they are built into every modern Linux kernel. Docker just made them usable.

Under the Hood · The Kernel07 / 20

What does the kernel actually look like?

The kernel is the core of an operating system — the privileged layer between your programs and the physical hardware. Every container on a host shares this one kernel, so it pays to know what lives inside it. Your programs run in user space and can only reach hardware by asking the kernel through system calls.

The kernel is one of the most important concepts to understand for containers, Docker, Kubernetes, Linux and system design.

1. What is a kernel?

The kernel is the core software of an operating system that directly manages the computer's hardware and provides services to applications — the middle layer between applications and hardware:

+----------------------------------+
|        Applications              |
|  Java | Python | Chrome | nginx  |
+----------------------------------+
|        System Libraries          |
|       libc | JVM | etc.          |
+----------------------------------+
|             KERNEL               |
| Process Management               |
| Memory Management                |
| File Systems                     |
| Networking                       |
| Device Drivers                   |
| Security                         |
+----------------------------------+
|             HARDWARE             |
| CPU | RAM | Disk | Network | GPU |
+----------------------------------+

Applications don't directly control the hardware. Instead:

Java application
      |  system call
      v
    Kernel
      |
      v
    Hardware

2. Why do we need a kernel?

Imagine a Java program wants to read a file with Files.readString(Path.of("data.txt")). Java doesn't tell the SSD "give me these bytes" directly — the request reaches the kernel:

Java → JVM → (system call) → Kernel → filesystem
     → storage driver → SSD

The kernel coordinates all of this.

3. Process management

Chrome, Java, Docker, PostgreSQL and nginx all want CPU time. The kernel's scheduler decides which process/thread runs on which core:

             Kernel Scheduler
        +-----------+-----------+
       CPU0        CPU1        CPU2
        |           |           |
      Java        Chrome     PostgreSQL

That's why multiple programs appear to run simultaneously.

4. Memory management

On a 16 GB machine, the kernel manages physical RAM, virtual memory, page tables, allocation, protection, swapping and memory mapping. Each process gets its own virtual address space:

Java process — virtual address space
+-------------------+
| Code | Heap       |
| Stack | Libraries |
+-------------------+
        |  kernel maps virtual → physical RAM
        v

This is why one process normally cannot read another process's memory.

5. File system management

When Java runs Files.readString(Path.of("/tmp/a.txt")), the kernel walks: Path → filesystem → disk blocks → storage driver → SSD. It supports filesystems such as ext4, XFS, Btrfs, NTFS and ZFS.

6. Networking

When your app runs socket.connect(server), the kernel handles the networking stack:

Java → Socket API → Kernel → TCP/IP
     → network driver → Ethernet/Wi-Fi → Network

It manages TCP, UDP, IP, routing, interfaces, sockets, firewalling and packet processing.

7. Device management

Applications don't directly drive the CPU, SSD, GPU, keyboard, NIC or USB devices. The kernel talks to hardware through device drivers:

Application → Kernel → Device Driver → Hardware
Java → Kernel → NVMe driver → NVMe SSD

8. System calls

Applications request kernel services through system calls — open(), read(), write(), close(), fork(), exec(), mmap(), socket(), connect():

Application
     |  system call
     v
+----------------+
|     Kernel     |
+----------------+
     |
     v
 Hardware / resources

The Java API (e.g. Files.readString) hides these details from you.

9. User space vs kernel space

This is extremely important for containers. Operating systems separate the two:

+---------------------------+
|        User Space         |
| Java | Python | nginx     |
| PostgreSQL                |
+---------------------------+
|       Kernel Space        |
| Scheduler | Memory mgr    |
| Network stack | FS | Drivers |
+---------------------------+
|         Hardware          |
+---------------------------+

Applications run in user space; the kernel runs in kernel space with far greater privilege. An app can't normally execute arbitrary privileged hardware operations.

10. Why containers share the kernel

This connects directly to chroot and BSD Jails:

                 Linux Kernel
       +-----------+-----------+
   Container A  Container B  Container C
     Java         nginx       PostgreSQL

Containers share the same kernel — they don't each carry their own. That's one reason they're lightweight. Compare a VM, where every VM has its own guest kernel:

                 Hypervisor
        /            |            \
     VM A          VM B          VM C
  Linux Kernel  Linux Kernel  Linux Kernel

11. How Docker isolates containers that share one kernel

Linux provides kernel features that carve up the shared kernel:

              Linux Kernel
       +-----------+-----------+
   Namespaces   cgroups   capabilities
   visibility   resources  privileges
                              + seccomp (syscalls)

Namespaces control what a process can see (PID, network, mount, user, IPC, UTS). cgroups control how much it can use (CPU, memory, PIDs, I/O). Capabilities control which privileged operations it may perform. seccomp controls which system calls it can make. This is why understanding the kernel is fundamental to understanding containers.

20. Kernel vs Operating System

These aren't the same thing. The kernel is not the entire OS:

Ubuntu
├── Linux Kernel
├── GNU tools
├── systemd
├── libraries
├── apt
└── applications / desktop

"Linux" technically refers to the kernel; "Ubuntu" is a Linux distribution built around it.

21. The connection to the rest of this module

Kernel
  +-- processes / memory / filesystem / networking / devices
  +-- namespaces  → containers
  +-- cgroups     → resource limits
  +-- capabilities
  +-- system calls

Historically:
chroot → BSD Jail → Linux namespaces + cgroups
       → container runtimes → Docker / Kubernetes

In one sentence: the kernel is the privileged core of the operating system that manages CPU, memory, processes, filesystems, networking and hardware, while providing controlled interfaces — system calls — for user-space applications to use those resources.

User programs never touch hardware directly — they ask the kernel through system calls.

Process scheduler

Decides which process runs on each CPU core and for how long — the illusion that everything runs at once.

Memory manager

Hands out and protects RAM: virtual memory, paging, and keeping one process from reading another's memory.

Virtual file system

One uniform interface over many filesystems and devices — the Unix idea that "everything is a file".

Network stack

TCP/IP, routing, sockets, and firewalling — how packets get in and out of the machine.

Device drivers

Speak the language of disks, GPUs, and network cards on behalf of user programs.

System-call interface

The guarded doorway between user space and kernel space. Every file, network, or process request passes through it.

🔑

For Docker, the two chips that matter are namespaces and cgroups. A container is just an ordinary process that the kernel shows a private view of these subsystems to — its own PIDs, mounts, and network — while everyone still shares the same kernel.

The VM Side · Guest OS08 / 20

What is a guest OS?

When you run a virtual machine, the hypervisor hands it virtual hardware and you install a complete operating system inside it. That installed OS is the guest OS: it has its own kernel, drivers, init system, system libraries, and background services — and it believes it owns a real machine.

Everything inside the orange box is a full operating system — duplicated in every single VM.
📦

What a guest OS includes

  • Its own kernel — a second kernel running on top of the host's.
  • Init system + services — systemd, logging, cron, sshd, and more, all booting up.
  • System libraries — the shared libraries the app links against.
  • Drivers — for the virtual hardware the hypervisor presents.
  • A full userland — shell, package manager, utilities.
⏳

Why that is expensive

  • Gigabytes of disk — a whole OS image per VM.
  • Hundreds of MB of RAM idle — spent on OS services, not your app.
  • Minutes to boot — because an entire OS starts up.
  • Patched separately — every guest OS needs its own updates.
  • Duplicated ×N — ten VMs means ten copies of the OS.
✦

A container has no guest OS. It reuses the host's already-running kernel and ships only the app plus its libraries. That single difference is why containers are measured in megabytes and seconds instead of gigabytes and minutes.

Deep Dive · Engine vs Hypervisor09 / 20

Docker Engine vs Hypervisor — in detail.

Both let many workloads share one physical machine — but they work at completely different layers. A hypervisor virtualizes hardware to run guest operating systems; the Docker Engine orchestrates isolated processes on the host's existing kernel.

🧱

Hypervisor

Virtualizes the hardware

Software that carves one physical machine into virtual machines by emulating CPU, memory, and devices. Each VM gets virtual hardware and runs its own guest OS — giving strong, hardware-level isolation.

  • Type 1 (bare-metal) — runs directly on hardware: VMware ESXi, Microsoft Hyper-V, KVM.
  • Type 2 (hosted) — runs on a desktop OS: VirtualBox, VMware Workstation.
  • Runs virtual machines — each boots a full operating system.

The easiest way to understand AWS EC2 is to think of the hypervisor as the layer that divides one physical AWS server into multiple isolated virtual machines.

One important clarification: AWS does not use a single hypervisor implementation for every EC2 generation. Older generations used Xen; modern EC2 uses the AWS Nitro System, where much of the traditional virtualization, networking and security work is moved into dedicated hardware and Nitro components.

1. Start with a physical AWS server

Imagine AWS has a physical server in a data center:

Physical AWS Server
──────────────────────────────────────
CPU:       64 physical cores
RAM:       512 GB
Storage:   NVMe SSD
Network:   100 Gbps
──────────────────────────────────────

AWS doesn't want one customer to consume the entire server. Virtualization lets AWS divide it into multiple EC2 instances:

                Physical Server
                       │
                Hypervisor / Nitro
                       │
       ┌───────────────┼───────────────┐
       │               │               │
     EC2 A           EC2 B           EC2 C
   4 vCPU/16GB     8 vCPU/32GB     2 vCPU/8GB

Each customer sees their EC2 instance as if it were an independent computer.

2. What exactly is a hypervisor?

A hypervisor is software/hardware that manages virtual machines and controls access to physical resources — a traffic controller between virtual machines and physical hardware.

             EC2 Instance
        ┌──────────────────┐
        │ Linux            │
        │ Java Application │
        │ Docker           │
        └────────┬─────────┘
                 │
                 ↓
        Virtual CPU / RAM / NIC
                 │
        ┌────────▼─────────┐
        │ Hypervisor/Nitro │
        └────────┬─────────┘
                 │
                 ↓
        Physical Hardware

The EC2 operating system doesn't directly control the physical AWS server. It interacts with virtual hardware, and AWS controls how that virtual hardware maps onto physical resources.

3. What happens when you launch an EC2?

aws ec2 run-instances \
  --image-id ami-xxxx \
  --instance-type m7i.large

Your request reaches the EC2 control plane:

AWS CLI
   │
   ↓
EC2 API
   │
   ↓
AWS Control Plane

AWS determines the Availability Zone, physical host, instance type, AMI, networking configuration, storage, security groups, IAM role, and more.

4. Instance type determines virtual hardware

Suppose you select m7i.large. Conceptually AWS defines something like:

m7i.large
├── 2 vCPU
├── 8 GiB RAM
├── Network capability
└── EBS storage capability

Your operating system sees only its assigned virtual resources:

$ lscpu
CPU(s): 2

It does not see the entire physical machine (64 cores, 512 GB RAM).

5. How does CPU virtualization work?

Physical CPU          EC2 Instance
Core 0                vCPU 0
Core 1                vCPU 1
Core 2 ...
Core 63

The virtualization layer maps those virtual CPUs to physical CPU resources:

EC2 A                    Physical CPU
─────                    ────────────
vCPU 0 ────────────────→ Core 17
vCPU 1 ────────────────→ Core 18

But don't treat this as a permanent vCPU 0 = Core 17 mapping — the underlying scheduling is more sophisticated. The guest OS believes it has CPUs, while AWS controls how those virtual CPUs execute on the physical CPU.

6. What about RAM?

The physical machine has 512 GB; your instance sees 8 GB. The virtualization layer ensures your VM cannot access another customer's memory:

Physical RAM
┌─────────────────────────────────────────────┐
│ Customer A │ Customer B │ Customer C         │
│   8 GB     │   16 GB    │    32 GB           │
└─────────────────────────────────────────────┘

Customer A cannot execute read(Customer_B_memory). This isolation is fundamental to AWS's multi-tenant architecture.

7. How does the EC2 OS boot?

An AMI contains what's needed to create the instance's root volume, including the OS image:

AMI
 │
 ├── Linux filesystem
 ├── Kernel / boot configuration
 ├── Packages
 └── Configuration
       │
       ↓
   Root volume
       │
       ↓
   EC2 instance

AWS creates/attaches the required storage and presents virtual devices to the instance, which then boots just like a physical computer from the OS's perspective.

8. What does the hypervisor actually expose?

                 EC2 Linux
                    │
       ┌────────────┼────────────┐
       │            │            │
     vCPU         vRAM         vNIC
       │            │            │
       └────────────┼────────────┘
                    │
              Virtualization
                    │
                    ↓
          AWS physical resources

The OS thinks a CPU, memory, network card and block device are present — but those devices are virtualized/paravirtualized and ultimately backed by AWS infrastructure.

9. What about networking?

Suppose your EC2 has private IP 10.0.1.25 and runs curl https://example.com:

Application
    ↓
Linux network stack
    ↓
Virtual NIC (ENI)
    ↓
Nitro networking hardware
    ↓
AWS network
    ↓
Internet Gateway / NAT / etc.
    ↓
Internet

The ENI (Elastic Network Interface) provides the logical network identity: private IP, public/Elastic IP, MAC address, security groups and subnet association.

10. Where does the Security Group work?

Internet
   │
   ↓
AWS networking
   │
   ↓
Security Group
   │
   ├── TCP 22   → ALLOW
   ├── TCP 80   → ALLOW
   └── TCP 3306 → DENY
   │
   ↓

Security Groups are implemented as part of AWS's networking infrastructure rather than as an iptables rule inside your Linux machine. Even if the OS is compromised, AWS's network-level controls still exist outside the guest OS.

11. What about EBS?

The OS might see /dev/nvme0n1, but that doesn't mean a physical disk is attached to that server:

EC2
 │ virtual block device
 ↓
Nitro / AWS storage networking
 │
 ↓
EBS infrastructure
 │
 ↓
Physical storage

This is why you can stop an EC2 instance and later start it again while retaining its EBS-backed root volume.

12. Modern EC2: the Nitro System

It is inaccurate to describe all modern EC2 simply as "a hypervisor running on a physical server." Modern EC2 uses the AWS Nitro System:

                EC2 instance
                     │
          ┌──────────┼──────────┐
          │          │          │
         CPU        RAM       Devices
          │          │          │
          └──────────┼──────────┘
                     │
              Nitro System
          ┌──────────┼──────────┐
          │          │          │
       Nitro Card  Nitro SSD   Nitro
       Networking  Controller  Security
                     │
                     ↓
              AWS infrastructure

Nitro is dedicated hardware and software providing virtualization, networking, storage I/O, security/isolation and management — reducing infrastructure software running on the host CPU.

13. Why did AWS build Nitro?

In traditional virtualization a large hypervisor handles many responsibilities. AWS moved much of that into dedicated hardware:

                 Physical server
                       │
        ┌──────────────┼──────────────┐
        │              │              │
      CPU/RAM       Nitro Card      Storage
        │              │              │
        │         Networking/I/O     │
        └──────────────┬──────────────┘
                       │
                  EC2 instances

This improves performance, isolation, security, scalability and host efficiency.

14. What about "bare metal" EC2?

EC2 bare metal
        │
        ↓

        │
        ↓
Your OS

There isn't a traditional customer-visible VM layer between your OS and the physical CPU. Useful for direct hardware access, specialized licensing, nested virtualization and very high-performance workloads.

15. Does AWS use the hypervisor to create S3, Lambda, RDS?

No — not every AWS service is Hypervisor → EC2 → service. Different services use different infrastructure:

     ↓                       ↓

     ↓                       ↓

     ↓

Don't generalize "AWS uses the hypervisor to create every AWS resource" — that's not accurate. S3 is a distributed object-storage service, not "an EC2 instance with a disk."

18. What happens if your EC2 crashes?

EC2 instance          EBS volume
     X                     ✓
     │
     ↓
Kernel crash

AWS infrastructure still exists and can terminate/restart/recreate the instance depending on configuration. If the root filesystem is EBS-backed, the persistent storage survives the instance lifecycle — a fundamental cloud idea: compute and persistent storage can be separated.

The virtualization layer ensures CPU, memory, network/device and storage-access isolation, plus security boundaries between customers.

Interview-quality answer

"How does AWS create an EC2 instance using virtualization?" — "AWS runs EC2 on physical servers using the Nitro System on modern instance generations. When we launch an EC2 instance, the EC2 control plane selects suitable underlying infrastructure and provisions an isolated virtual machine with the CPU, memory and virtual devices corresponding to the selected instance type. Nitro provides the virtualization, networking, storage and security functions, while the guest OS sees standard virtual hardware and boots from the selected AMI. The instance's network interface connects it to the VPC, and EBS provides persistent block storage. The virtualization and hardware isolation ensure multiple customers can safely share the same physical infrastructure while each EC2 instance behaves like an independent server." The key chain to remember: Physical server → Nitro virtualization → EC2 VM → OS → application — and EC2 is only one AWS service; AWS does not create every resource by creating an EC2 VM.

Docker Engine

Virtualizes the OS (processes)

Not a hypervisor. A daemon and runtime that turn an image into an isolated process on the host's existing kernel — no virtual hardware, no guest OS — using kernel namespaces and cgroups.

  • dockerd — the daemon exposing the REST API.
  • containerd — the high-level container runtime.
  • runc — spawns the container using namespaces + cgroups.
  • Runs containers — each is just a process.

Let's take the exact command and follow it all the way from your keyboard to the nginx process:

docker run -d --name my-nginx -p 8080:80 nginx

Correction to the simplified picture: in modern Docker, dockerd delegates container lifecycle work to containerd, and containerd invokes an OCI runtime such as runc. dockerd itself does not directly call the Linux kernel for every container operation.

1. You type the command

docker       → Docker CLI
run          → create + start container
-d           → detached / background
--name       → container name = my-nginx
-p 8080:80   → host port 8080 → container port 80
nginx        → image to use
Shell → docker executable

The docker executable is a client. It does not itself create the Linux container.

2. Docker CLI finds the Docker Engine

The CLI needs to know which daemon to talk to. On Linux it typically uses the Docker Engine API Unix socket:

docker CLI
    |  HTTP request over Unix socket
    v
/run/docker.sock
    |
    v
dockerd
ls -l /var/run/docker.sock   # /var/run usually points into /run

3. What API request does docker run generate?

It's not one API call — the CLI performs several operations:

docker run
    +---- POST /containers/create
    +---- POST /containers/{id}/start
    (plus image ops if the image is missing)

The create request carries config roughly like:

{
  "Image": "nginx",
  "name": "my-nginx",
  "ExposedPorts": { "80/tcp": {} },
  "HostConfig": {
    "PortBindings": {
      "80/tcp": [ { "HostPort": "8080" } ]
    }
  }
}

Exact JSON varies by Docker API version and CLI behaviour.

4. dockerd receives the request

docker CLI → (Docker Engine API) → dockerd

dockerd is a long-running daemon:

ps aux | grep dockerd
systemctl status docker

5. First question: do I have the nginx image?

docker images
REPOSITORY   TAG       IMAGE ID
nginx        latest    abc123...

If nginx:latest isn't local, Docker must pull it.

Why Docker Was Needed

Problems Docker Solves11 / 20

VMs solved isolation. Docker solves what they didn't.

01

↻ "It works on my machine"

Code runs on a dev laptop but breaks in test/prod because of a different library, OS patch, or missing dependency. Each VM image is hand-configured and drifts.

◆ Docker's answer

The app and all its dependencies are baked into a single image defined by a Dockerfile. The same image runs identically on laptop, CI, and production.

02

▦ VMs are heavy and slow

A full guest OS per VM — a handful of VMs per server, GBs each, minutes to boot, real patching work.

◆ Docker's answer

Containers share the host kernel, so one server runs dozens or hundreds of containers, each starting in seconds with a fraction of the resources.

03

⚒ Slow, inconsistent setup

Onboarding meant following a long, error-prone doc — install Postgres 14, this Redis, that Python…

◆ Docker's answer

docker compose up recreates the entire stack — database, cache, app — identically in one command, in minutes.

04

↗ Inefficient scaling & deployment

Scaling a VM app means cloning whole machines; deployments are large and slow.

◆ Docker's answer

Images are small, layered, and cached — shipping a new version moves only the changed layers. Starting another copy is nearly instant.

Why "it works on my machine" happens: drift.

Drift is when environments that were supposed to be identical gradually become different over time — because each one is changed and maintained independently. It's the single biggest reason code passes in one environment and breaks in the next.

When VMs are hand-configured, someone runs a few commands on one VM — and forgets to run exactly the same ones on the others. Over months, the differences pile up.

Don't configure each environment by hand. Define the environment once in a Dockerfile, build it into one immutable image, and run that same image everywhere.

A Brief History15 / 20

From mainframe VMs to Docker to Podman.

Containers didn't appear overnight. The core ideas — isolation, resource limits, and packaging — were invented across five decades, from 1960s mainframes to today's rootless engines. Here is the lineage.

Virtualization Container ancestor Docker Standards / Orchestration Podman

The problem in the 1960s

A mainframe cost millions and ran one program at a time. IBM's research lab in Cambridge wanted many users to share one machine as if each had their own computer — the birth of time-sharing and virtualization.

The key idea: the Virtual Machine Monitor

CP-40 (and then CP-67 on the System/360-67) introduced a control program that gave each user a complete virtual copy of the hardware:

            Real Hardware (S/360)
                    |
             Control Program (CP)   ← the first hypervisor
        +-----------+-----------+
     Virtual      Virtual      Virtual
     Machine 1    Machine 2    Machine 3
     (CMS)        (CMS)        (CMS)

Why it mattered

Each VM had its own virtual CPU, memory and devices, fully isolated from the others. This is the ancestor of every hypervisor today (VMware, KVM, Hyper-V) — and the earliest form of "running isolated environments on one computer."

Containers came decades later and take a different route (share the kernel instead of emulating hardware), but the goal — isolated environments on one machine — was born here.

1964–1967
Virtualization

IBM CP-40 / CP-67 — the first virtual machines

IBM's research systems ran multiple "virtual" copies of a mainframe at once, letting many users time-share one machine. This is where virtualization — and the whole idea of running isolated environments on one computer — was born.

From research to product

VM/370 turned the CP/CMS research into a supported commercial operating system for the System/370. Each user logged into a full virtual System/370 running the lightweight CMS single-user OS.

          System/370 hardware
                  |
             VM/370 (CP)
        +---------+---------+
     Virtual   Virtual   Virtual
     S/370     S/370     S/370
     + CMS     + CMS     + a guest OS

What made it powerful

A virtual machine was so faithful that you could even run another copy of VM/370 inside a VM (nested virtualization). Businesses used it to run test and production systems side by side, and to keep old software running on new hardware.

VM/370's descendants (z/VM) still run on IBM mainframes today — over 50 years of continuous virtualization lineage.

1972
Virtualization

IBM VM/370 goes commercial

The VM/370 operating system gave each user a complete virtual System/370. Virtualization moved from research to a mainstream, supported mainframe product that businesses relied on for decades.

1. Normal Linux filesystem view

Imagine your machine has:

/
├── bin/
├── etc/
├── home/
│   └── pk/
├── lib/
├── tmp/
├── usr/
│   ├── bin/
│   └── lib/
└── var/

Normally, when a process does open("/etc/passwd", O_RDONLY), the kernel interprets /etc/passwd relative to the system's root, so the process sees the host filesystem.

2. What does chroot do?

Suppose we create /myroot/ with its own bin/ etc/ lib/ app/. Then calling chroot("/myroot") changes the process's root directory. From that process's perspective / now corresponds to /myroot/, so:

open("/etc/config", ...);   →  resolves to  /myroot/etc/config
                            (not the host's /etc/config)

That's the fundamental idea.

3. Simple example

/tmp/myroot/
├── etc/
│   └── myconfig
└── app/
    └── hello

$ sudo chroot /tmp/myroot /app/hello

Inside the process, / is now /tmp/myroot. So cat /etc/myconfig actually reads /tmp/myroot/etc/myconfig. The process thinks /etc/myconfig, but the host kernel resolves it underneath.

4. What is actually happening?

A process has filesystem-related state maintained by the kernel:

Process
   |
   +-- current working directory
   +-- root directory
   +-- file descriptors

Normally process.root = /. After chroot("/tmp/myroot"), conceptually process.root = /tmp/myroot, and all pathname resolution uses that root:

Process asks for  /etc/passwd
        |
        v   kernel pathname resolution
process root = /tmp/myroot
        |
        v
/tmp/myroot/etc/passwd

The application itself doesn't need to know that / has been changed.

5. Why was this useful?

You can construct a miniature filesystem containing only what an app needs — bin/sh, etc/app.conf, lib/libc.so, app/program — then run chroot app-root /app/program. The application sees only that tree rather than the entire host filesystem. This is the beginning of the filesystem-isolation idea used by containers.

6. But there is a major security problem

chroot does not mean "this process is securely trapped inside this directory." It means more narrowly: "for normal pathname resolution, use this directory as the process's filesystem root."

A sufficiently privileged process can potentially escape. chroot traditionally requires root privileges; a classic escape involves changing the working directory before calling chroot and then using directory-traversal / file-descriptor tricks to reach the old filesystem.

chroot ≠ security sandbox. This distinction is extremely important.

7. Why chroot isn't enough for containers

Run chroot /container-root /bin/bash and the process has a different filesystem root — but ps aux can still see host processes, ip addr still sees host interfaces, and free -m still sees host memory.

chroot
  |
  +-- isolates filesystem view
  X-- doesn't isolate processes
  X-- doesn't isolate network
  X-- doesn't isolate users
  X-- doesn't limit CPU/memory

9. Mount namespace + chroot

Modern runtimes create a separate mount namespace so the container gets its own view of mounted filesystems, then establish a root filesystem and change the process's root — traditionally with chroot or, more commonly today, pivot_root. The key combination: mount namespace + isolated root filesystem = container filesystem view.

10. PID namespace

Host                    Container
PID 2000  ───────────>  PID 1  (application)
PID 2001  ───────────>  PID 2  (worker)
PID 2002  ───────────>  PID 3  (child)

The application believes it is PID 1, while the host kernel knows it as PID 2000. chroot cannot provide this.

11. Network namespace

Host namespace          Container namespace
eth0 10.0.0.10   ⇄      eth0 172.17.0.2

The container gets its own interfaces, routing table, IP addresses, firewall rules and ports. chroot → filesystem isolation; network namespace → network isolation.

12. User namespace

Container             Host
UID 0   ───────────>  UID 100000
UID 1   ───────────>  UID 100001
UID 2   ───────────>  UID 100002

A process can be UID 0 (root) inside the container while mapped to an unprivileged host UID. So container root ≠ host root — a significant isolation improvement.

13. cgroups solve a different problem

Namespaces answer "what can the process see?" cgroups answer "how much resource can it consume?" — e.g. CPU: 2 cores, RAM: 1 GB, PIDs: 100, I/O limits. Namespaces → isolation; cgroups → resource control.

14. Capabilities

Linux splits the all-powerful root into fine-grained capabilities (CAP_NET_ADMIN, CAP_SYS_ADMIN, CAP_CHOWN, CAP_KILL, CAP_NET_RAW…). A container can run as root inside its namespace with the dangerous capabilities removed, reducing the blast radius of a compromised app.

15. seccomp

Application → system call → seccomp filter
                              +-- allowed → kernel
                              +-- blocked → denied

The runtime restricts which syscalls the process may make. The full isolation stack: namespaces (what it sees) + cgroups (how much) + capabilities (what it can do) + seccomp (which syscalls).

16. How Docker fits into this

docker run nginx isn't simply chroot /some/dir nginx. A modern runtime roughly: (1) prepares a root filesystem, (2) creates namespaces, (3) configures mounts, (4) networking, (5) cgroups, (6) capabilities, (7) seccomp, (8) sets the container root, (9) executes the app.

                 Host Kernel
       +-------------+-------------+
    Container A   Container B   Container C
     nginx          java          redis
       +-------------+-------------+
                 shared kernel

Containers generally share the host kernel. A VM doesn't.

  Host OS                   Hypervisor

  +-- Container A           +-- VM2 (Guest OS)
  +-- Container B

Containers are lighter because they don't require a complete guest kernel per environment.

18. Why chroot is historically important

Calling chroot an ancestor of containers is reasonable historically — but don't equate the two.

The mental model to remember

          Container
    +---------+---------+
 What see?  How much?  What can do?

    |
 filesystem/processes/network/users
    +-- chroot / rootfs

chroot changes a process's filesystem root, so absolute paths like /etc/config resolve relative to a different tree. It provides filesystem-view isolation but is not, by itself, a security boundary. Modern containers build on the same idea and add namespaces (process/network/user), cgroups (resources), and capabilities + seccomp (privilege/syscall limits) on a dedicated root filesystem.

1979
Container ancestor

chroot arrives in Unix V7

The chroot system call could confine a process to a subtree of the filesystem — the earliest ancestor of containers. It shipped in BSD in 1982 and is still used to build isolated environments today.

Why x86 was "impossible" to virtualize

The x86 instruction set had ~17 privileged instructions that failed silently instead of trapping when run in user mode — so a classic hypervisor couldn't cleanly intercept them.

VMware's breakthrough: binary translation

VMware Workstation (1999) scanned guest kernel code at runtime and rewrote the problematic instructions on the fly, while letting safe user-mode code run natively at full speed.

Guest OS code
     |
 binary translator  ← rewrites unsafe privileged instrs
     |
 runs on real x86 CPU (safe code runs natively)

Then it went to the data center

ESX Server (2001) was a bare-metal (type-1) hypervisor installed directly on the hardware — no host OS underneath:

Type 2 (Workstation)      Type 1 (ESX)
  Hardware                  Hardware
  Host OS                   Hypervisor
  Hypervisor app            +-- VM
  +-- VM                    +-- VM

Later, Intel VT-x and AMD-V added hardware support that made privileged instructions trap properly — so binary translation became unnecessary and modern hypervisors (KVM, Hyper-V) rely on the CPU directly.

1999
Virtualization

VMware brings VMs to the PC

VMware Workstation cracked the hard problem of virtualizing x86, putting virtual machines on commodity hardware. ESX Server (2001) took VMs into the data center and launched the modern virtualization industry.

chroot, but a real boundary

FreeBSD Jails (introduced with the jail(2) syscall) fixed chroot's biggest weakness: escape. A jail confines processes to a filesystem subtree and restricts what they can see and do system-wide.

What a jail isolates

Jail
 +-- own root filesystem   (like chroot)
 +-- own set of processes  (can't see host PIDs)
 +-- own users / root      (jailed root ≠ real root)
 +-- bound to specific IP address(es)
 X-- cannot load kernel modules, reboot, see other jails

Why it's a direct container ancestor

A jailed root is powerful inside the jail but nearly harmless outside it — the exact model containers use today. Jails delivered OS-level isolation (one shared kernel, many isolated environments) years before Linux had the pieces to match it.

Solaris Zones (2004) and later Linux namespaces + cgroups are the same idea, refined and split into composable kernel primitives.

2000
Container ancestor

FreeBSD Jails — real OS-level isolation

Jails partitioned a single FreeBSD system into isolated mini-environments, each with its own files, users, and network. It's a direct conceptual parent of the Linux containers we use now.

Xen — paravirtualization (2003)

Instead of expensively emulating hardware, Xen modified the guest OS to cooperate with the hypervisor via "hypercalls." This paravirtualization was far faster than binary translation on the x86 of the day.

        Xen Hypervisor (bare metal)
                |
   +------------+------------+
  Dom0 (control)   DomU    DomU   (guest OSes)

Xen powered the first big public clouds — including the original Amazon EC2.

Solaris Zones / Containers (2004–05)

On the container side of the family, Sun's Zones partitioned one Solaris kernel into many isolated environments, adding fine-grained resource controls (CPU/memory caps) — a preview of what Linux cgroups would later provide.

Two branches advancing at once: Xen matured full-machine virtualization, while Zones proved OS-level isolation at enterprise scale.

2003–2005
Virtualization

Xen & Solaris Zones mature the field

The open-source Xen hypervisor (2003) powered the first big clouds, while Solaris Containers/Zones (2004–05) proved OS-level isolation at enterprise scale — pushing both the VM and container ideas forward.

Two missing ingredients arrive in Linux

Containers need answers to two separate questions. Linux got a dedicated primitive for each:

MechanismAnswers
NamespacesWhat can a process see?
cgroupsHow much can it use?

cgroups (control groups)

Started by Google engineers as "process containers," merged into the kernel in 2008. cgroups cap and account CPU, memory, block-I/O and the number of PIDs per group of processes:

cgroup: web-app
  cpu.max   = 2 cores
  memory.max = 1 GB
  pids.max  = 100

Namespaces

Added incrementally (mount, PID, network, IPC, UTS, user…). Each gives a process its own private view of one kind of global resource — its own process tree, its own network stack, its own hostname.

Namespaces + cgroups are the raw kernel features. LXC, then Docker, packaged them into something usable.

2006–2008
Container ancestor

cgroups & namespaces land in Linux

Google engineers built "process containers" — later renamed cgroups — to cap CPU and memory per process; it merged into the Linux kernel in 2008. Combined with namespaces, Linux finally had the raw ingredients for containers.

Gluing the kernel pieces together

LXC (Linux Containers) was the first widely used userspace tool that combined namespaces + cgroups into a working "container" with a single set of tools.

LXC
 +-- namespaces  → isolated view (PID, net, mount, ...)
 +-- cgroups     → resource limits
 +-- rootfs      → the container's filesystem
 = a running Linux container

What LXC gave you

Something close to a lightweight VM: a full init system and multiple processes, isolated on the host kernel — no guest OS to boot.

The gap it left

LXC was low-level and system-specific. There was no standard way to package, version and share a container — you couldn't easily hand someone "the exact same environment." That missing packaging layer is precisely the gap Docker filled in 2013.

Docker's first releases actually ran on top of LXC before replacing it with its own libcontainer.

2008
Container ancestor

LXC — the first native Linux containers

LXC (Linux Containers) glued cgroups and namespaces into usable containers. It worked, but stayed low-level and hard to share — there was no easy way to package and ship an app.

The killer feature: the image

The kernel primitives existed for years. Docker's insight was packaging: a portable, versioned, layered image you build once and run identically anywhere.

Layered image (copy-on-write)
  Layer 4  your app code
  Layer 3  pip install deps
  Layer 2  apt-get install python
  Layer 1  base OS (e.g. debian)
  ── layers are cached & shared between images ──

Build once, run anywhere

A Dockerfile describes the build; the resulting image runs the same on a laptop, CI, and production — ending "works on my machine."

Dockerfile → docker build → image → docker run → container

Why it exploded

Docker added a great CLI, a build system, and Docker Hub — a registry to push and pull images by name. Containers went from an expert-only kernel feature to an everyday developer tool. Announced by Solomon Hykes at PyCon 2013, out of the dotCloud PaaS.

Early Docker used LXC as its execution backend; it later swapped to its own libcontainer (2014), which became the basis of the OCI runtime spec.

2013
Docker

Docker is born

Solomon Hykes unveils Docker at PyCon (out of the dotCloud PaaS). Built at first on LXC, it added the killer feature: portable, layered images you build once and run anywhere. Containers went from arcane to everyday.

Docker 1.0 — production ready

Docker declared its API and format stable, and replaced LXC with its own libcontainer, talking to the kernel directly instead of through a third-party tool.

Kubernetes — the outer loop

Docker runs containers well on one machine. But production means many machines, restarts, scaling and networking. Google open-sourced Kubernetes (based on its internal "Borg") to orchestrate containers across a cluster.

Docker  = inner loop   → build & run a container here
Kubernetes = outer loop → schedule, scale, heal
                           containers across many nodes
        Kubernetes control plane
     +----------+----------+
   Node 1     Node 2     Node 3
   [pods]     [pods]     [pods]   ← containers run inside pods

They are different layers, not competitors. Kubernetes schedules work; a container runtime (containerd, CRI-O) actually runs the containers on each node.

2014
Docker

Docker 1.0 & Kubernetes

Docker hits production-ready 1.0 and swaps LXC for its own libcontainer. The same year, Google announces Kubernetes to orchestrate containers across clusters — the outer loop to Docker's inner loop.

Avoiding vendor lock-in

As containers took off, the industry needed guarantees that an image built by one tool would run on another. Two bodies formed in 2015:

Open Container Initiative (OCI)

Defines vendor-neutral specifications so tools interoperate:

OCI specs
 +-- image-spec    → how an image is laid out (layers, config)
 +-- runtime-spec  → how to run a container from a rootfs
 +-- distribution-spec → how registries serve images

Docker donated its image format and the runc runtime as the reference implementations.

CNCF (Cloud Native Computing Foundation)

A neutral home (under the Linux Foundation) to steward cloud-native projects — Kubernetes, containerd, Prometheus, and many more.

From here on, "container image" means an OCI image — interchangeable across Docker, Podman, containerd, CRI-O and Kubernetes.

2015
Standards

OCI & CNCF standardize everything

The Open Container Initiative defines vendor-neutral image and runtime specs, and the CNCF forms to steward cloud-native projects. From here on, container images are interchangeable across tools.

Splitting Docker into layers

Docker extracted its core runtime, containerd, and donated it to the CNCF. "Docker" the product now sits on top of shared, standard infrastructure:

docker CLI
     |
 dockerd (daemon: build, images, networks)
     |
 containerd  (manages container lifecycle, images)   ← CNCF
     |
 runc  (OCI runtime: actually creates the container)  ← OCI
     |
 Linux kernel (namespaces, cgroups)

Why the split matters

Kubernetes talks to containerd directly through the CRI (Container Runtime Interface) — it doesn't need the full Docker daemon. So the low-level engine that actually runs containers is now shared by Docker and Kubernetes.

This is why Kubernetes was able to "deprecate Docker" (the dockershim) in 2020 without breaking anything — it kept using containerd underneath, and your OCI images ran unchanged.

2016–2017
Standards

containerd becomes shared infrastructure

Docker extracts its core runtime, containerd, and donates it to the CNCF. The low-level engine that actually runs containers is now shared industry infrastructure — used by Docker and Kubernetes.

Removing the daemon

Docker relies on a long-running root daemon (dockerd) that every command talks to — a single privileged process and a single point of failure. Podman (Red Hat) is daemonless: each podman command forks the container directly (via conmon + runc/crun).

Docker              Podman
 docker CLI          podman CLI
    |                   |  (no daemon)
 dockerd (root)      fork container directly
    |                   |
 containerd/runc     conmon + crun

Rootless containers

Using user namespaces, Podman lets an ordinary user run containers where in-container root maps to their unprivileged host UID — so a container breakout doesn't yield host root.

Drop-in compatible

Podman runs the same OCI images and mirrors the Docker CLI so closely that alias docker=podman often just works.

Same images, same commands — the choice of engine (Docker vs Podman) no longer dictates your images.

2018–2019
Podman

Podman 1.0 — daemonless & rootless

Red Hat ships Podman 1.0 (Jan 2019): a Docker-compatible engine with no background daemon and the ability to run containers without root. A security-focused alternative that runs the exact same OCI images.

Rootless becomes the default expectation

Running containers without root is now standard practice, not a niche security feature. Both Docker (rootless mode) and Podman support it, backed by user namespaces and tools like slirp4netns/pasta for unprivileged networking.

Interchangeable by design

          OCI image (built by anyone)
     +----------+----------+----------+
   Docker     Podman    containerd   CRI-O
     |           |           |          |
     +-----------+-----------+----------+
              same container runs

Docker Desktop and Podman Desktop give the same GUI/CLI experience across Windows, macOS and Linux. You pick the tool that fits your policy; the image and the running container stay identical.

The through-line of the whole timeline: isolation, resource limits and packaging — now standardized (OCI), safer by default (rootless), and portable across every major engine.

2022 → today
Podman

Rootless & interchangeable is the norm

Podman Desktop arrives and rootless containers become standard practice. Docker and Podman both build and run the same OCI images — you pick the tool, and the containers stay interchangeable.

Docker vs Kubernetes17 / 20

Different layers — not competitors.

🐳

Docker

Build & run a container, one machine

Docker's job is to package an app into an image and run containers, typically on one machine. It answers: how do I turn my app into a container and run it here?

☸️

Kubernetes (K8s)

Orchestrate many containers across many machines

A container orchestrator. Manages large numbers of containers across a cluster and answers the operational questions Docker alone doesn't:

  • Scheduling — which server runs each container
  • Scaling — auto add/remove replicas
  • Self-healing — restart or reschedule failures
  • Load balancing & service discovery
  • Rolling updates & rollbacks
  • Config & secret management
A K8s cluster: nodes hold pods, and pods hold containers.
🤝

They work together — you build the image with Docker (or Podman/Buildah), push to a registry, and Kubernetes pulls & runs it across the cluster via a container runtime. Docker is the inner loop; Kubernetes is the outer loop.

Practical · Module 01 Example19 / 20

A Python web app + Redis, in two files.

Dockerfile
# Base image: official, small, version-pinned Python.
FROM python:3.12-slim

# Everything below runs inside /app.
WORKDIR /app

# Copy deps first so the pip layer is cached.
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Now copy the rest of the source code.
COPY . .

# Document the port the app listens on.
EXPOSE 5000

# Default command when a container starts.
CMD ["python", "app.py"]
docker-compose.yml
services:
  web:                       # our Python web app
    build: .                 # build image from Dockerfile
    ports:
      - "5000:5000"          # host 5000 -> container 5000
    environment:
      REDIS_HOST: redis      # service name below
    depends_on:
      - redis                # start redis before web

  redis:                     # counter storage
    image: "redis:7-alpine"   # official image
    volumes:
      - redisdata:/data      # persist across restarts

volumes:
  redisdata:                # Docker-managed named volume
▶

One command: docker compose up — builds the web image, pulls redis:7-alpine, creates a private network so web reaches redis by name, mounts the redisdata volume, and starts redis before web. Open http://localhost:5000 and refresh — the counter goes up.

Key Takeaways20 / 20

Eight things to remember.

1

Docker packages apps into portable, lightweight containers.

One image, identical across laptop, CI, and production.

2

Containers share the host kernel; VMs boot a full OS.

Megabytes vs gigabytes; seconds vs minutes.

3

Docker solved what VMs did not.

Consistent ships-with-the-app environments, high density, fast startup, one-command setup. Isolation alone was never the gap.

4

VMs and Docker are complementary.

Containers commonly run inside VMs. VM = hardware isolation; Docker = app portability on top.

5

Different vendors, open standards.

VMs from VMware, Microsoft, Oracle, KVM, etc. Docker from Docker, Inc., with standards under OCI/CNCF.

6

Today's alternatives to Docker.

Podman, containerd, CRI-O, and Buildah — all build or run the same OCI images.

7

Docker ≠ Kubernetes.

Docker builds and runs containers on one machine; Kubernetes orchestrates many across a cluster. Inner loop vs outer loop — not enemies.

8

The CLI talks to the daemon.

Which manages images and containers. Every docker command is one REST call to dockerd.
