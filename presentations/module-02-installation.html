Step 01 / 04

Which Docker do I need?

Two products, one engine underneath. The right choice depends on whether you're on a desktop or a headless Linux server.

Desktop vs Engine01 / 09

Same engine, two ways to run it.

Both give you the Docker CLI and container runtime. Docker Desktop wraps the engine in a friendly app with a GUI for laptops; Docker Engine is the bare engine you install directly on Linux servers.

🖥️

Docker Desktop

Easiest option for Windows & macOS

A single installer that bundles the engine, CLI, Compose, and a graphical dashboard. On Windows/macOS it runs a small Linux VM behind the scenes so Linux containers work natively.

🐧

Docker Engine

The core engine for Linux servers

Just the daemon, CLI, and containerd — no GUI. This is what you install on production Linux hosts and cloud VMs, where it runs directly on the host kernel.

 Docker DesktopDocker Engine
Best forWindows & macOS (and Linux desktops)Linux servers & cloud VMs
Graphical UIYes — dashboard & settingsNo — CLI only
Includes ComposeYes, built inYes (plugin)
Runs Linux containers viaA lightweight Linux VMThe host kernel directly
Resource controlsGUI sliders (CPU/memory)Host / systemd config
💡

On a laptop? Install Docker Desktop. Deploying to a Linux server? Install Docker Engine. Either way you get the same docker command and run the same images.

Cloud Deep Dive

Docker runs in AWS — controlled from your Windows machine

EC2, Spot, Lightsail, ECR + EC2, and ECS/Fargate — with complete Terraform files, every command, and the EC2-vs-Fargate distinction.

If the requirement is "Docker runs only in AWS, but I control/test it from my Windows local machine", there are several practical approaches. The key distinction:

  • EC2 / Lightsail VM — the Docker daemon runs on a VM; your local Docker CLI can control it over SSH.
  • Fargate — there is no Docker daemon you control. You build/push an image and ECS runs it.
  • Spot EC2 — same Docker workflow as EC2, but the machine can be interrupted.

Docker officially supports connecting the local CLI to a remote Docker daemon through SSH, so you don't need to expose Docker's TCP port publicly.

Approaches at a glance

EC2 On-Demand is billed only while running (per-second billing, 60-second minimum), so stopping the instance when you're done is useful for a dev environment.

1. EC2 — simplest and most flexible

Windows Laptop
     │  Docker CLI + SSH
     ▼
AWS EC2
     └── Docker Engine
           ├── Spring Boot
           ├── PostgreSQL
           ├── Redis
           └── Kafka

For Mumbai, t4g is available in ap-south-1.

Step 1 — Create EC2

AWS Console → EC2 → Launch instance. Name docker-lab, AMI Ubuntu Server 24.04 LTS, instance t4g.micro (ARM64), storage 20 GB gp3. If your images are x86-only, choose t3.micro instead.

Step 2 — Security Group

For basic Docker remote management you only need SSH — TCP 22 — Source: My IP. To test a Spring Boot app from your laptop/browser add TCP 8080 — My IP. For a public web app you could add TCP 80 / 443.

Do not open Docker port 2375 to the Internet. Docker warns that insecure remote daemon access can allow unauthorized, potentially root-level control.

Step 3 — Connect to EC2 (PowerShell)
ssh -i C:\keys\docker-lab.pem ubuntu@<EC2_PUBLIC_IP>
Step 4 — Install Docker (on EC2)
sudo apt update
sudo apt install -y docker.io
sudo systemctl enable --now docker

# run docker without sudo
sudo usermod -aG docker ubuntu
exit                                   # log out, then reconnect
ssh -i C:\keys\docker-lab.pem ubuntu@<EC2_PUBLIC_IP>

# test
docker version
docker run --rm hello-world

2. Control EC2 Docker directly from Windows

On your local Windows machine you need the Docker CLI. Then create a Docker context pointing at the remote daemon over SSH:

docker context create aws-docker `
  --docker "host=ssh://ubuntu@<EC2_PUBLIC_IP>"

docker context use aws-docker
docker context show          # → aws-docker
docker ps                    # lists containers running on EC2, not locally

Docker's SSH context forwards requests to the remote Docker socket. Now run a container from your laptop — it runs on EC2:

docker run -d --name nginx -p 8080:80 nginx
docker ps
# open http://<EC2_PUBLIC_IP>:8080
docker run -d --name myapp -p 8080:8080 my-spring-app:latest

The image must be available to the remote daemon. For production-style deployments, use ECR rather than relying on a local image.

3. ECR + EC2 — the better workflow

Windows ──docker build──▶ Image ──docker push──▶ AWS ECR ──docker pull──▶ EC2 ──▶ Container

Step 1 — ECR → Repositories → Create repository → my-spring-app.

# Step 2 — build locally
docker build -t my-spring-app .

# Step 3 — authenticate to ECR
aws ecr get-login-password --region ap-south-1 | \
docker login --username AWS --password-stdin \
  <ACCOUNT_ID>.dkr.ecr.ap-south-1.amazonaws.com

# Step 4 — tag
docker tag my-spring-app:latest \
  <ACCOUNT_ID>.dkr.ecr.ap-south-1.amazonaws.com/my-spring-app:latest

# Step 5 — push
docker push \
  <ACCOUNT_ID>.dkr.ecr.ap-south-1.amazonaws.com/my-spring-app:latest
# Step 6 — on EC2: login, pull, run
aws ecr get-login-password --region ap-south-1 | \
docker login --username AWS --password-stdin \
  <ACCOUNT_ID>.dkr.ecr.ap-south-1.amazonaws.com

docker pull <ACCOUNT_ID>.dkr.ecr.ap-south-1.amazonaws.com/my-spring-app:latest
docker run -d --name myapp -p 8080:8080 \
  <ACCOUNT_ID>.dkr.ecr.ap-south-1.amazonaws.com/my-spring-app:latest
# test http://<EC2_PUBLIC_IP>:8080

4. Lightsail — simpler alternative

Windows ──SSH──▶ Lightsail Linux VM ──▶ Docker ──▶ Container

AWS Console → Lightsail → Create instance → Linux/Unix → Ubuntu → smallest suitable plan. Connect via the Lightsail browser SSH console, then:

sudo apt update
sudo apt install -y docker.io
sudo systemctl enable --now docker
docker run -d -p 80:80 nginx
# access http://<LIGHTSAIL_PUBLIC_IP>

You can also use ssh ubuntu@<LIGHTSAIL_IP> or the same Docker SSH-context approach. Advantage: simpler UI/networking. Disadvantage: EC2 gives more flexibility for AWS learning.

5. Fargate — no EC2 to manage

Windows ──docker build──▶ ECR ──▶ ECS ──▶ Fargate ──▶ Container

There is no VM to SSH into and no Docker daemon for your local CLI to control.

# Step 1 — build
docker build -t myapp .

# Step 2 — push to ECR
docker tag myapp:latest <ACCOUNT_ID>.dkr.ecr.ap-south-1.amazonaws.com/myapp:latest
docker push <ACCOUNT_ID>.dkr.ecr.ap-south-1.amazonaws.com/myapp:latest

Step 3 — ECS → Clusters → Create → ECS cluster. Step 4 — create a task definition (Launch type: Fargate, small CPU/memory, container image from ECR, container port 8080). Step 5 — create an ECS Service:

Cluster → Service → Task → Fargate → Container

Test (if you assign a public endpoint/load balancer):

curl https://<endpoint>/api/health

Cost note: for one tiny dev container, Fargate isn't necessarily cheapest — you can also pay for networking, load-balancing and CloudWatch logging. ECS Express Mode simplifies deployment but you still pay for the underlying Fargate, load balancer, logs and data transfer.

6. EC2 Spot — cheapest EC2 approach

Spot EC2 → Ubuntu → Docker → Spring Boot

Docker install and usage are exactly the same as EC2; only the purchase option differs. AWS can interrupt Spot when capacity is needed (documented up to 90% savings), and gives an interruption notice before reclaiming capacity.

Good for: learning, development, temporary testing, batch, non-critical environments. Not for: production databases, important persistent services, anything that cannot tolerate interruption.

7. What I would use for development

For Spring Boot + PostgreSQL + Redis + Kafka + Angular/React:

Option A (simplest)    EC2 t4g.micro → Docker Compose (Spring Boot + PostgreSQL + Redis)
Option B (cheapest)    EC2 → Docker Compose (+ Kafka) — scale the instance up when needed
Option C (AWS learning) Local Windows → docker build + AWS CLI → ECR → ECS → Fargate

Kafka + PostgreSQL + Redis + Spring Boot together may be too much for a tiny instance — you'd want more RAM if running them all at once. If your goal is specifically learning AWS container deployment, Option C is better than simply getting the cheapest Docker server.

EC2 vs Fargate — the key difference

With EC2 you run real Docker commands against the remote daemon: docker ps, docker run, docker stop, docker logs, docker exec. With Fargate you do not — instead: ECR → task definition → service → task. This distinction drives the architecture choice.

Destroying everything

cd 01-ec2-docker      && terraform destroy    # EC2, IAM, SG, subnet, RT, IGW, VPC
cd 02-ec2-spot-docker && terraform destroy
cd 03-lightsail-vm    && terraform destroy
cd 05-ecs-fargate     && terraform destroy    # important — don't leave a running service

What to build first (recommended order)

Step 1  EC2 + Docker      Terraform → VPC → EC2 → Docker → Nginx
Step 2  Remote Docker CLI Windows CLI ──SSH──▶ EC2 Docker Engine (ps/run/logs/stop/rm)
Step 3  ECR               Windows → docker build → ECR → EC2 → docker pull
Step 4  ECS/Fargate       Docker → ECR → ECS → Fargate

Corrections: don't automatically pick t4g.micro for Spring Boot + PostgreSQL + Redis + Kafka together — container count and memory matter more than CPU, and t4g is ARM64 so images must support ARM64. Start with t4g.micro → Docker → nginx, then Spring Boot, then scale up before adding PostgreSQL/Redis/Kafka. Also don't use a NAT Gateway for this lab — a public subnet with an Internet Gateway is simpler and avoids an expensive component.

Step 02 / 04

Installation

Pick your operating system below. Windows and macOS use the Desktop installer; Linux uses the official convenience script.

Installation02 / 09

Install Docker on your OS.

Install Docker Desktop on Windows

  1. Download Docker Desktop from docker.com/products/docker-desktop.
  2. Run the installer and follow the prompts.
  3. When asked, enable WSL 2 — the recommended backend.
  4. Launch Docker Desktop and wait for the whale icon to read "Docker Desktop is running".
🐳

Why WSL 2? Windows can't run Linux containers natively, so Docker Desktop uses the Windows Subsystem for Linux 2 — a real Linux kernel — as its backend. It's faster and lighter than the older Hyper-V VM approach.

Install Docker Desktop on macOS

  1. Download Docker Desktop from docker.com/products/docker-desktop.
  2. Choose the build for your chip — Apple Silicon (M-series) or Intel.
  3. Open the .dmg and drag Docker into Applications.
  4. Launch Docker and wait for the whale icon to say "Docker Desktop is running".
🍎

Same idea as Windows. macOS also can't run Linux containers directly, so Docker Desktop runs a small Linux VM under the hood. Pick the installer that matches your CPU or the app will run slowly under emulation.

install-docker.sh
# Remove any old versions
sudo apt-get remove docker docker-engine docker.io containerd runc

# Install using the official convenience script
curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh

# (Optional) Run docker without sudo
sudo usermod -aG docker $USER
newgrp docker
🔎

What just happened? The convenience script adds Docker's official package repository and installs the engine, CLI, and containerd. Adding your user to the docker group lets you run docker commands without sudo.

Key Takeaways06 / 09

Three things to remember.

1

Desktop for Windows/macOS; Engine for Linux servers.

Same CLI and images either way — the difference is packaging and the GUI.

2

docker run hello-world is the definitive test.

If it prints the greeting, your install can pull an image and run a container.

3

Know info, ps, ps -a, and images cold.

They answer "what's running and what do I have?" — your daily inspection kit.
